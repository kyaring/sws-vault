- 根因：`cmd/swsvault/main.go:32` `var commit = "dev"`，`versionText()`（`main.go:325-337`）依赖 Go 的隐式 VCS 戳记（`debug.ReadBuildInfo` 的 `vcs.revision`）。**Go 在 git worktree 里不做 VCS 戳记**：我在同一提交上做了对照实验——普通 clone 里构建会输出 `e5b8546f2618047b5ddc231cc57b8267c9893203`（`go version -m` 含 `vcs.revision`），而 worktree 里构建的二进制 `go version -m` 没有 vcs 信息。卡片指定的构建位置（`/tmp/rv-sv01`）与开发者自己的 worktree（`/root/work/sws-vault-wt/v1-core`）都是 worktree，所以**按 README 的构建命令永远拿不到 commit**。
- 影响：验收卡一.3 与任务书六.3 明确要求「能输出 commit」，交付未满足；也影响后续运维卡的构建可追溯。
- 建议修复：构建时显式注入，例如 `go build -trimpath -ldflags "-X main.commit=$(git rev-parse HEAD)"`，并同步更新 README 与验收命令。

### 2. [一般] `/v1/resolve` 的 `allow_resolve` 门禁没有任何测试

- 反向验证 R1：把 `handlers.go:185` 的 `!bd.AllowResolve` 判定去掉后，`./internal/api/... ./internal/cli/... ./cmd/...` 全绿。
- 代码行为本身是对的（临时探针实测：未开 `allow_resolve` 的 secret → `403 {"error":"forbidden"}`，响应不含值），所以这是**回归保护缺失**，不是行为缺陷。
- 修复：加一条「未开 allow_resolve → 403 且不泄露值」的测试（现有 `resolve_test.go` 只覆盖 `allow_resolve:true` 的路径）。

### 3. [一般] `/v1/resolve` 的 `Cache-Control: no-store` 没有任何测试

- 反向验证 R2：把 `handlers.go:213` 换成 `public, max-age=86400` 后，测试全绿。
- 代码行为本身是对的（冒烟实测响应头为 `Cache-Control: no-store`）。
- 修复：在 resolve 测试里断言响应头（顺带断言错误路径不返回明文）。

### 4. [一般] 主密钥宽权限拒绝启动/加载没有任何测试

- 反向验证 R9：把 `main.go:125` 与 `keyring.go:56` 的 `Perm()&0077 != 0` 判定改成恒假后，`go test -count=1 ./...` 全绿。
- 代码行为本身是对的（两处检查都在，`keyring.go` 对所有版本密钥文件逐个检查）。
- 修复：加测试——把 master.key 置为 0644 后 `LoadKeyringAt` 必须报错（serve 侧可对提取出的校验函数做单测，避免真的要起服务）。

### 5. [建议] client 令牌校验是 SQL 哈希等值查询，不是字面意义的常数时间比较

- `server.go:113-119`：`sha256(token)` 后 `WHERE token_hash=?` 查库，没有 `subtle.ConstantTimeCompare`。
- 卡片二.4 字面要求「比较时用常数时间比较」。因为比的是**哈希值**（不可逆、无逐字节可猜的明文），且索引查找时序无法用于恢复 256 位随机令牌，实际风险极低，也是 Go 生态通行做法。
- 若要与卡片字面一致，可先按哈希取行、再用 `subtle.ConstantTimeCompare` 复核哈希；或明确把该要求解释为「存哈希即满足」。**不视为阻塞**。

### 6. [建议] SSRF 边界情形行为正确，但没有回归测试

卡片二.5 点名要求检查的 userinfo、主机名大小写、末尾点、IPv6 字面量、十进制 IP，以及通配符/子域/端口白名单，我全部用临时探针实测（见第二节第 5 条的表格），行为都正确，但仓库里**一条测试都没有**（`engine_test.go` 只覆盖未授权主机、loopback、metadata、重定向、1 MB 上限、DNS 钉住、脱敏）。同样，调用方 `X-Auth-*` 必须被丢弃也没有测试（我用探针确认后端看到 `X-Auth-Token=""`）。
- 修复：把这些情形补成表驱动测试（成本低、回归价值高）。

### 7. [建议] 面板 cookie 属性与 8 小时绝对超时没有测试

`admin.go:122,179` 的 HttpOnly / SameSite=Strict / 条件 Secure，以及 `admin.go:212` 的 8 小时绝对超时，都没有断言（现有测试只覆盖空闲超时、CSRF、TOTP 重放、锁定）。代码是正确的。

### 8. [建议] 未鉴权的 `/admin/assets/` 开启了目录列表

- 探针实测：不带任何 cookie `GET /admin/assets/` → `200`，正文是嵌入文件系统的目录列表（`<a href="admin.css">admin.css</a>`）。
- `server.go:88` 用 `http.FileServer` 直接挂在 `/admin/assets/` 上，既没有走 `adminSession`，也没有关闭目录列表。泄露面仅「一个文件名」，风险很低。
- 修复：改成只暴露具体文件的路由，或对目录请求返回 404。

### 9. [建议] 面板与 list 返回 `bindings.username` 原文，与 preview 打码不一致

- `save()` 对 login 类型把 preview 设为打码用户名（`handlers.go:124-125`），但 `bindings.Username` 仍以原文随元数据返回（`Metadata.Bindings`），面板「绑定策略」列也直接展示 bindings JSON（`admin.go:111`）。
- 卡片只把「值」定义为明文，所以不违反二.1；但既然 preview 认为用户名需要打码，元数据里原样回传就自相矛盾。建议至少确认这是有意为之并写进 `docs/security.md`。
